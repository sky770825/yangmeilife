## 一、結論

目前網站可以當作「靜態展示與內容架構原型」，但還不能以「65 項功能都已完成、可由後臺控制」的狀態直接上架。

已經穩定的部分：

- 60 個根目錄頁面均可正常回應，沒有 404。
- 390px 手機寬度未發現全頁橫向溢位。
- 首頁、分類總覽、廠商卡片、6 個簡易估算器、4 個娛樂功能已有可操作介面。
- 廠商卡片已有撥號、Google Maps 導航、官網與 LINE 連結。
- 分類、功能、廠商、更新紀錄已開始資料化，生成器可以同步靜態頁面。

不能直接上架為完整平台的原因：

- 47 個「正式功能頁」全部仍標記需要核實，其中 33 頁只有說明卡與頁內搜尋，沒有名稱所暗示的實際功能。
- `vendor-admin.html`、`test-image-upload.html`、`booking.html` 目前只是說明模板，沒有登入、表單、圖片上傳、審核、發布或 API。
- 11 個廠商分類只有 4 個有店家，另外 7 個是空分類。
- 11 家現有店家中有 7 家使用 Unsplash 通用圖庫照片，不是該店實景。
- 首頁有 69 個 JavaScript 點擊區塊、0 個真正的 `<a>` 連結，會影響 SEO、鍵盤操作與開新分頁。
- 舊版封存後臺自行比對明碼密碼，甚至曾要求匿名權限讀取密碼欄位，不能直接恢復到正式環境。
- 首頁宣告的 `og-image.png` 實體檔案不存在，也沒有 `robots.txt`、`sitemap.xml`、`404.html`、正式建置流程或 CI 驗證。

## 五、後臺上架控制規劃

### 5.1 建議架構

保留目前公開站的靜態頁面優勢，後臺另外建立受保護的管理應用。第一階段建議使用專用 Supabase 專案：

```text
管理者 / 編輯 / 店家
        ↓ Supabase Auth
獨立後臺 /admin
        ↓ RLS + API
Postgres 資料庫 + Storage 圖片 + 審核紀錄
        ↓ 僅輸出 published 資料
公開網站 / 靜態生成或唯讀 API
```

正式環境最好不要與其他專案共用 Supabase。若一定要共用，仍須維持 `yangmeilife_` 前綴、完整 RLS、獨立 Storage 路徑與環境隔離。

### 5.2 角色與權限

| 角色 | 可做的事 | 不可做的事 |
|---|---|---|
| Super Admin | 帳號、角色、分類、全站設定、審核、發布、回復版本 | 無 |
| Content Editor | 編輯頁面、文章、公告、橫幅、SEO、送審 | 不可管理角色或直接改安全設定 |
| Reviewer | 核對來源、退回修改、核准內容 | 不可刪除歷史版本 |
| Vendor Owner | 編輯自己的店家、服務、營業時間、圖片並送審 | 不可直接發布、不可查看其他店家私密資料 |
| Viewer/Analyst | 查看統計與稽核結果 | 不可修改內容 |

登入必須使用 Supabase Auth 的 email OTP、Magic Link 或正式密碼流程。禁止在自建資料表保存可讀取的明碼密碼，也禁止前端持有 service-role key。

### 5.3 發布狀態

```text
draft → submitted → in_review → approved → scheduled → published
                  ↘ changes_requested
published → unpublished → archived
```

規則：

- 店家只能建立 `draft` 與送出 `submitted`。
- Reviewer 可以核准或退回，只有管理者可以立即發布或排程。
- 每次發布都要保存 revision、操作人、時間、變更內容與回復點。
- 橫幅與活動要有 `starts_at`、`ends_at`，到期自動下架。
- 公開網站只能讀取 `published` 且未過期的資料。

- 不直接熱連結 Facebook、Instagram、官網或 Postimg 圖片作正式資產。
- 未取得授權或未記錄來源的圖片不可發布。
- 圖片上不可包含未同意公開的人臉、電話、車牌或個資。

## 七、分批施工順序

### Batch 0：公開面止血

- 建立「可公開清單」，先保留已核准外連、4 個娛樂功能、6 個已驗證估算器與 4 個有資料的廠商分類。
- 33 個模板頁改成不公開、明確即將推出，或完成後再上線。
- 隱藏直接管理、測試與更新路由。
- 修首頁 `<a>`、桌機底部導覽、OG 圖、404、robots、sitemap、法律頁。

完成標準：使用者不會把說明模板誤認為真功能，公開路由沒有內部工程資訊。

### Batch 1：後臺基礎

- 建立專用 Supabase、Auth、角色、RLS、資料表、Storage、版本與 audit log。
- 建立 staging / production 環境，金鑰只放環境變數。
- 先完成店家、媒體、橫幅、功能頁的 CRUD 與預覽。

完成標準：店家只能改自己的草稿；公開站只能讀取已發布資料；管理者可回復版本。

### Batch 2：素材與店家資料

- 收集 11 家 Logo、封面與圖庫，先替換 7 張通用圖。
- 補緯經度、營業時間、價格日期、資料來源與授權。
- 空分類達到至少 3 家核實店家後再公開。

完成標準：每個公開店家都有授權封面、alt、Logo、電話、地址、導航、來源與核實日期。

### Batch 3：高價值生活資訊

- 優先串接天氣、垃圾車、公車、停車等官方資料。
- 每頁加入更新時間、錯誤狀態、重試、資料來源與非即時 fallback。

完成標準：頁面不是固定假資料，離線或 API 失敗時也不會顯示過期內容為即時資訊。

### Batch 4：個人工具與社群

- 決定個人工具使用 localStorage 或會員雲端同步。
- 社群功能先完成登入、審核、檢舉、封鎖、刪除與個資政策。

完成標準：新增、編輯、刪除、歷史、匯出與權限流程均可測試，不只顯示說明卡。

### Batch 5：全站 QA 與發布

- 375/390/768/1024/1440 視窗測試。
- 鍵盤、讀屏、44px 觸控、對比、reduced-motion 測試。
- 內外連結、圖片、表單、權限、RLS、發布排程、回復與備份演練。
- Lighthouse/Core Web Vitals、SEO、結構化資料與分享預覽測試。

完成標準：0 個壞內連結、0 張壞圖、0 個未授權管理入口、0 筆未核實高風險資料公開。

## 八、驗收門檻

- 公開站只顯示 `published`、未過期且通過審核的資料。
- 所有管理與測試頁必須登入且依角色授權。
- 所有店家圖片有授權、alt、來源、尺寸與本機/CDN 版本。
- 所有店家電話可撥、地址可導航、官網/LINE 有效。
- 所有即時資訊都有來源與最後更新時間。
- 所有估算器有公式版本、資料日期、測試案例與免責聲明。
- 所有手機主要操作區至少 44×44px，內容不被固定導覽遮住。
- 首頁與分類入口使用真正超連結，可鍵盤操作、開新分頁與被搜尋引擎理解。
- 發布、下架、排程、退回與版本回復都有 audit log。
- 正式發布前完成資料庫備份與回復演練。
